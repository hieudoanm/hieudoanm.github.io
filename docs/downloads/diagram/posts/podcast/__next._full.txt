19:T447,Upload uses resumable, multipart uploads directly to object storage with a presigned URL issued by the Upload Service, so the API never proxies the audio bytes; a completed upload registers an episode object with the pipeline. The Audio Pipeline is a set of queue-driven workers: each episode goes through validation (format detection, duration, corrupt-frame check), normalization (loudness to the loudness target), and transcoding into the delivery formats. Transcoding is CPU-expensive, so jobs are chunked per episode and parallelized; each rendition is produced independently and progress is tracked so a worker crash resumes the missing renditions rather than restarting. Output is written to the Audio Store, and when all renditions are ready the episode transitions to published, which triggers feed regeneration and notification. The pipeline backpressures via the queue — ingest rate is capped by worker pool size — and failed episodes are retried with exponential backoff then quarantined for manual review. 1b:T42e,The RSS feed is the public contract, so it must be cheap to fetch and stable. Feeds are generated by the Feed service from the episode catalog and rendered as static XML that is cached aggressively — the feed URL is served from a CDN with a short TTL and revalidation, because thousands of podcast clients poll every show hourly. To keep feed regeneration cheap, feed XML is built on publication events rather than on every request: when an episode publishes, the show's cached feed is invalidated and rebuilt once. 1c:T44d,Progress is tracked as per-user, per-episode state — played seconds, completed flag, and a server-side record of the last position — so a listener can switch from phone to car to desktop and resume mid-episode. Reads dominate at resume time, so recently listened episodes are cached per user. Conflict handling matters for offline playback: the client keeps a local position and merges with the server on reconnect, taking the later position or the most complete "listened" flag. Completed episodes are marked distinctly and drive auto-next behavior and recommendations. Privacy is a first-class constraint — listening history is sensitive — so the store is partitioned per user, retention is bounded, and aggregation for analytics is done on anonymized data.
