# dbml (Go) — Functional Requirements

This page expands [`01-requirements.md`](../01-requirements.md) into individual functional requirements. Each requirement states what dbml must do from the user's perspective; the matching behaviour contract lives in [`02-features.md`](../02-features.md) and the matching user goal in [`03-user-stories.md`](../03-user-stories.md).

Priorities follow [`README.md`](../README.md) §4 and [`02-features.md`](../02-features.md) §2: **P0** is required for the first usable release, **P1** is an enhancement. dbml is a software demonstration, not a full database modeling tool, and it claims no regulatory compliance.

## FR-001 — DBML parsing (P0)

dbml reads Database Markup Language source and builds one internal AST before any output is produced. The parser (`internal/dbml/parser.go`) recognises `Project` header lines, `Table` blocks with column definitions and bracket settings, `Enum` blocks, `Index` lines inside tables, top-level `Ref:` relationships with `<`/`>` direction indicators, and `Note:` comments.

The parser is transport-agnostic: it knows nothing about CLI flags, HTTP routes, or MCP, and it never hard-codes output formats ([`04-architecture.md`](../04-architecture.md) §2). SQL, Mermaid, and SVG generation all walk the same AST ([`05-data-model.md`](../05-data-model.md) §3).

## FR-002 — SQL generation (P0)

`Project.ToSQL()` renders PostgreSQL-compatible DDL: a `-- Generated by dbml CLI` header, one `CREATE TABLE` per table with mapped column types and `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, and `DEFAULT` constraints, table-level `UNIQUE (...)` constraints for unique indexes, and `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ...` for every parsed reference.

The generated DDL is intended to be executable against PostgreSQL and usable in migrations and CI pipelines ([`00-overview.md`](../00-overview.md) §11).

## FR-003 — Mermaid generation (P0)

`Project.ToMermaid()` renders `erDiagram` syntax: one block per table with `PK`/`UK` key markers and `NOT NULL` flags, plus one relationship line per reference labelled with the reference name. The output is plain text usable in GitHub/GitLab Markdown and any Mermaid renderer, with no mermaid-cli or Node.js dependency ([`08-tech-stack.md`](../08-tech-stack.md) §4.5).

## FR-004 — SVG generation (P0)

`Project.ToSVG()` renders an ER diagram as vector graphics directly in Go: table and enum boxes on a fixed grid, key markers per column, and relationship curves between boxes. The result is a self-contained XML document requiring no external rendering tool such as Graphviz.

Per [`09-testing-strategy.md`](../09-testing-strategy.md) §3, SVG tests assert the output is well-formed XML.

## FR-005 — Multi-format conversion in one command (P0)

`dbml all` parses the input once and writes `initial_schema.sql`, `database-erd.mmd`, and `schema.svg` into an output directory (default: current directory), creating that directory when it does not exist. With the default input file in place, `dbml all` completes the whole conversion workflow with zero configuration ([`README.md`](../README.md) §5, Journey A).

## FR-006 — CLI commands (P0)

The Cobra CLI exposes `sql`, `mermaid`, `svg`, `all`, `serve`, and `mcp`, plus `help` and `--version`. The input file defaults to `schema.dbml`; `-o` selects an output file for the single-format commands; `-d`/`--output-dir` selects the output directory for `all`; `serve` accepts `--port`/`-p` and `--debug`.

A successful run prints where the output was written; every failure — missing input, too many arguments, unwritable output — prints a single actionable `dbml: ...` line on stderr. The process currently exits 0 even on failure (`main.go` discards the return value of `cmd.Execute()`), so callers must inspect stderr rather than the exit status ([`FEATURE-08-Error-Handling.md`](../02-features/FEATURE-08-Error-Handling.md) §5). The full command surface is specified in [`04-architecture.md`](../04-architecture.md) §4.2 and §7.

## FR-007 — HTTP server (P0)

`dbml serve` starts an HTTP server exposing a REST API: `POST /api/v1/convert`, `POST /api/v1/convert/sql`, and `POST /api/v1/convert/mermaid`. Requests may be JSON bodies, multipart form-data uploads (`file` or `dbml` fields), or a raw body containing DBML; responses are JSON with `sql`, `mermaid`, and `svg` fields.

When `formats` is omitted the server defaults to `sql` and `mermaid`. The complete route list, payloads, and status codes are specified in [`06-api-specification.md`](../06-api-specification.md).

## FR-008 — Health check (P0)

`GET /api/v1/health` returns HTTP 200 with `{"status":"ok","version":"dev"}` so operators and automation can confirm the process is alive. Health checks are part of the MVP definition of done ([`02-features.md`](../02-features.md) §4).

## FR-009 — OpenAPI document and Swagger UI (P1)

`GET /api/v1/openapi.json` serves an OpenAPI 3.0.3 document describing the convert, health, and docs routes, and `GET /api/v1/docs` serves a Swagger UI page that loads that document. Both are produced by the same binary with no separate documentation build ([`README.md`](../README.md) §8).

## FR-010 — MCP server (P1)

`dbml mcp serve` runs a Model Context Protocol server over stdio speaking JSON-RPC 2.0. It implements `initialize`, `ping`, `tools/list`, and `tools/call`, and advertises four tools — `dbml_sql`, `dbml_mermaid`, `dbml_svg`, and `dbml_parse` — each taking a single required `dbml` string argument.

Tool handlers delegate to the same parser and generators as the CLI and HTTP handlers; no MCP logic reaches into `internal/dbml` ([`04-architecture.md`](../04-architecture.md) §4.4).

## FR-011 — Actionable error reporting (P0)

Every failure path reports what failed, which file or request was involved, and enough context to fix it. CLI errors are wrapped with context (`parse DBML: ...`, `write output: ...`) and printed as `dbml: <message>` on stderr (the exit status is currently 0 even on failure — see [`FEATURE-08-Error-Handling.md`](../02-features/FEATURE-08-Error-Handling.md) §5); HTTP validation failures return HTTP 400 with a JSON `error` field; MCP failures return JSON-RPC error objects with code and message.

API responses never expose filesystem paths ([`06-api-specification.md`](../06-api-specification.md) §1), and complete error handling is required before MVP ([`02-features.md`](../02-features.md) §4).
