# US-009: Check server health

## Story

**As a** developer/operator
**I want** a cheap health check for the running HTTP server
**So that** scripts and CI can confirm the API is up before converting anything

## Acceptance scenarios

- **Given** `dbml serve --port 8080` is running, **When** `GET /api/v1/health` is requested, **Then** the response is HTTP 200 with `{"status":"ok","version":"dev"}`.
- **Given** a preflight script, **When** the health endpoint returns 200, **Then** the script proceeds to `POST /api/v1/convert` knowing the process is serving requests.
- **Given** the server is not running, **When** the health request is attempted, **Then** the connection fails immediately (nothing is listening), distinguishing "process down" from a conversion error.
- **Given** the current router, **When** `GET /health` (the alias mentioned in `06-api-specification.md` §5 and [`12-operations.md`](../12-operations.md)) is requested, **Then** it is not registered and the router answers its default 404 — callers should use `/api/v1/health`.

## Notes

- The health check is required by the MVP definition of done ([`02-features.md`](../02-features.md) §4) and is FR-008.
- The `version` field reports `dev` for a default `make build`; it identifies the build, not the schema being converted.
- Liveness plus structured logs are the whole observability story in the initial release: no metrics, dashboards, or alerting yet ([`12-operations.md`](../12-operations.md), [`README.md`](../README.md) §8).
- The endpoint is unauthenticated like the rest of the API; MVP assumes a local, single-user deployment ([`06-api-specification.md`](../06-api-specification.md) §3).
