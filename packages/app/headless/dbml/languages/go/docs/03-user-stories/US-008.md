# US-008: Review conversion errors

## Story

**As a** developer
**I want** conversion failures to explain what went wrong and where
**So that** I can fix the input or the command without guessing

## Acceptance scenarios

- **Given** a typo in the command (`dbml sql missing.dbml`), **When** the command exits, **Then** stderr contains one line beginning `dbml: parse DBML: open file:` naming `missing.dbml`, stdout contains no success message, and the failure is detectable from stderr (the exit status is 0 regardless — see [`FEATURE-08-Error-Handling.md`](../02-features/FEATURE-08-Error-Handling.md) §5).
- **Given** an unwritable output path (`-o /nonexistent/dir/out.sql`), **When** the command exits, **Then** the error identifies the write step (`dbml: write output: ...`) rather than printing a bare failure.
- **Given** `POST /api/v1/convert` with malformed JSON, **When** the server replies, **Then** the status is 400 and the body is JSON with an `error` field describing the decode failure — never a filesystem path or stack trace.
- **Given** an invalid JSON-RPC line sent to `dbml mcp serve`, **When** the server replies, **Then** the response is a JSON-RPC error object with code `-32700` and the session continues.
- **Given** a successful run followed by a failing run in the same directory, **When** the second run exits, **Then** the failure is visible on stderr, so scripts and CI can detect it (exit codes do not distinguish the two runs — FEATURE-08 §5).

## Notes

- The error contract — what failed, which file/path was involved, enough context to fix it — is FR-011 in [`01-requirements/functional-requirements.md`](../01-requirements/functional-requirements.md) and is implemented per transport in [`FEATURE-08-Error-Handling.md`](../02-features/FEATURE-08-Error-Handling.md).
- API responses must never expose filesystem paths ([`06-api-specification.md`](../06-api-specification.md) §1); CLI errors must include them — the two transports have opposite path rules by design.
- One documented limitation: the tolerant parser skips some unclassifiable DBML instead of rejecting it, so not every malformed file produces an error (see US-010 and [`FEATURE-01-DBML-Parsing.md`](../02-features/FEATURE-01-DBML-Parsing.md)).
