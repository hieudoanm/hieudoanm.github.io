# US-006: Convert DBML via the HTTP API

## Story

**As a** developer
**I want** to convert DBML programmatically over HTTP
**So that** build scripts and services can obtain SQL, Mermaid, or SVG without shelling out to the CLI

## Acceptance scenarios

- **Given** the server is running (`dbml serve --port 8080`), **When** `POST /api/v1/convert` arrives with `{"dbml":"Table users { id integer [pk] }","formats":["sql","mermaid"]}`, **Then** the response is HTTP 200 JSON containing both `sql` and `mermaid` fields.
- **Given** no `formats` field, **When** `POST /api/v1/convert` arrives with valid DBML, **Then** the response defaults to `sql` and `mermaid`.
- **Given** `formats` includes `"svg"`, **When** the request is processed, **Then** the `svg` field contains a complete SVG document.
- **Given** a DBML file on disk, **When** `curl -F "file=@schema.dbml"` posts to `/api/v1/convert`, **Then** the uploaded content is converted and returned as JSON.
- **Given** a request with no DBML content, **When** it reaches `/api/v1/convert`, **Then** the response is HTTP 400 with `{"error":"dbml field is required"}` and no filesystem path appears in the body.
- **Given** the server, **When** `GET /api/v1/openapi.json` and `GET /api/v1/docs` are requested, **Then** the OpenAPI document and Swagger UI page describe and exercise the same endpoints.

## Notes

- The exact route list, request encodings, and status codes are specified in [`06-api-specification.md`](../06-api-specification.md) and implemented as documented in [`FEATURE-06-HTTP-Server.md`](../02-features/FEATURE-06-HTTP-Server.md).
- MVP is local and single-user with no authentication; treat the server as a local tool ([`06-api-specification.md`](../06-api-specification.md) §3).
- Each request is independent and stateless — there is no stored conversion state ([`04-architecture.md`](../04-architecture.md) §10).
