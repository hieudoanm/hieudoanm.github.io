# US-001: Parse a DBML file

## Story

**As a** developer
**I want** to point dbml at a DBML file and have it parsed into a single internal schema model
**So that** every output format is derived from one faithful representation of my schema

## Acceptance scenarios

- **Given** `schema.dbml` declaring tables, columns with settings, an enum, and a named `Ref:` relationship, **When** any conversion command runs (`dbml sql schema.dbml`), **Then** the file is read and parsed without any manual modelling step, and generation proceeds from the resulting `Project` AST.
- **Given** a file containing `//` comments and blank lines, **When** it is parsed, **Then** both are skipped and the parsed schema matches the same file without them.
- **Given** a column line `id integer [pk, increment]`, **When** it is parsed, **Then** the column records its name, type, primary-key flag, and remaining settings.
- **Given** a reference line `Ref: user_posts users.id < posts.user_id`, **When** it is parsed, **Then** the reference records both endpoints with the direction resolved to a referenced/referring pair.
- **Given** the input file does not exist, **When** `dbml sql missing.dbml` runs, **Then** stderr contains `dbml: parse DBML: open file: ...` naming the file (the process still exits 0 — see [`FEATURE-08-Error-Handling.md`](../02-features/FEATURE-08-Error-Handling.md) §5).

## Notes

- Parsing lives in `internal/dbml/parser.go` and is transport-agnostic: the CLI, HTTP handlers, and MCP tools all call the same entry points ([`04-architecture.md`](../04-architecture.md) §2).
- The parser is line-based and tolerant: constructs it cannot classify are skipped rather than rejected (see [`FEATURE-01-DBML-Parsing.md`](../02-features/FEATURE-01-DBML-Parsing.md) edge cases and US-010).
- Tests use real DBML input, not hand-built ASTs ([`09-testing-strategy.md`](../09-testing-strategy.md) §3).
- dbml is a software demonstration: it parses the documented subset of DBML, not the full dbml-lang specification.
